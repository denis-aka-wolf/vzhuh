# Разработка и текущее состояние

## Статус репозитория

Первый MVP добавляет базовые состояния ожидания и подключения поверх Flutter-шаблона. На текущем этапе:

- `lib/main.dart` содержит интерфейс ожидания, подключения и подтверждения входящего запроса;
- `lib/connection_service.dart` реализует TCP-соединение для частных IPv4-адресов и loopback;
- тесты покрывают видимые режимы, адресную политику и локальный цикл подключения/подтверждения;
- зависимости для шифрования, аутентификации, удалённого управления, хранения учётных записей или второго фактора отсутствуют;
- каталога с компонентом/службой Windows нет;
- Windows runner является платформенной оболочкой Flutter, а не сервером удалённого доступа.

Экран, мышь, клавиатура и команды не передаются. Текущий незашифрованный и неаутентифицированный протокол годится только для изолированного тестирования.

## Технологическая основа

- Flutter и Dart для текущего интерфейсного каркаса.
- Ограничение SDK Dart в `pubspec.yaml`: `^3.13.3`.
- Windows runner и CMake-конфигурация находятся в `windows/`.
- Репозиторий также содержит шаблонные платформенные каталоги Flutter для Android, iOS, Linux, macOS и Web. Их наличие само по себе не означает поддержку продукта.

Фактические версии Flutter SDK, Windows SDK, Visual Studio и поддерживаемые версии Windows следует закрепить перед настройкой CI и публикацией сборок.

## Подготовка среды и команды

Установите Flutter SDK, откройте PowerShell в корне репозитория и выполните:

```powershell
flutter --version
.\scripts\run-debug.ps1
```

Скрипт `scripts\run-debug.ps1` восстанавливает зависимости и запускает Windows-приложение в режиме debug. При необходимости можно запустить Flutter вручную:

```powershell
flutter pub get
flutter run --debug -d windows
```

Перед выпуском соберите и упакуйте Windows Release:

```powershell
.\scripts\deploy-production.ps1
```

Скрипт проверяет анализатором и тестами проект, выполняет `flutter build windows --release`, затем копирует **весь** каталог `build\windows\x64\runner\Release` в уникальный каталог `out\Vzhuh-<версия>-<время>`. Результат включает исполняемый файл, Flutter runtime и assets. Не переносите только `vzhuh.exe`. Существующий каталог результата не перезаписывается; результаты в `out\` исключены из Git.

```powershell
flutter analyze
flutter test
```

Release-пакет всё ещё содержит текущий MVP: протокол соединения незашифрован и не аутентифицирует стороны. Слово «production» в имени скрипта означает release-конфигурацию сборки, а не готовность к безопасному продуктивному или интернет-развёртыванию. Используйте её только в изолированной тестовой сети.

## Рекомендуемый порядок разработки

1. Уточнить границы MVP, разрешённые операции и платформу оператора.
2. Спроектировать модель доверия, идентичность станции, угрозы и ограничения прав.
3. Определить формат протокола и тестируемые требования к защищённому соединению до сетевой реализации.
4. Реализовать отдельно тестируемый Windows-компонент и минимальную поверхность привилегий.
5. Добавить вход, политику авторизации и аудит; затем интегрировать UI-клиент.
6. Добавлять варианты второго фактора с явным описанием внешних зависимостей и безопасной конфигурацией.
7. Проверить локальный сценарий, обработку отказов и отзыв доступа.
8. Только после независимой проверки безопасности документировать и включать внешний сценарий.

Не добавляйте неподтверждённые или незашифрованные механизмы управления ради демонстрации внешнего подключения.

## Контроль перед изменением

- Убедитесь, что документация и UI не обещают функции, которых нет в коде.
- Новые возможности должны иметь тесты и обновления соответствующих разделов в `docs/`.
- Секреты, реальные адреса устройств и учётные данные не добавляются в репозиторий.
- После изменения Dart/Flutter-кода выполните анализатор и тесты; документационные изменения не требуют перестройки приложения.

## Долги и неизвестные

- Нет утверждённой архитектуры приложения-оператора и службы Windows.
- Нет сетевого протокола, спецификации совместимости и механизма проверки идентичности станции.
- Не выбраны Windows API и модель привилегий для каждой удалённой операции.
- Не выбрана стратегия хранения учётных записей и восстановления доступа.
- Нет настроек и руководства по каналам SMS, электронной почты и Telegram.
- Нет CI, политики релизов, процедуры подписывания и процесса раскрытия уязвимостей.
