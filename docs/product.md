# Назначение и требования

## Краткое описание

Вжух (Vzhuh) — проект с открытым исходным кодом для локального удалённого администрирования рабочих станций Windows. Оператор должен иметь возможность подключаться к управляемой станции в одной сети или напрямую по её внешнему адресу `IP:порт`. Обязательный облачный сервис или сторонний ретранслятор не входит в целевой сценарий.

Проект рассчитан на использование владельцем устройства или уполномоченным администратором. Подключение должно быть заметным, проверяемым и ограниченным явно разрешёнными действиями.

## Реализованный MVP

Первый MVP предоставляет только базовую проверку сетевой связности:

- пользователь может запустить ожидание на выбранном локальном IPv4-адресе и порту;
- другой пользователь может инициировать подключение по частному IPv4-адресу;
- принимающий пользователь видит адрес источника и явно принимает или отклоняет запрос;
- соединение ограничено одним активным сеансом, который можно завершить из интерфейса;
- допускается `127.0.0.1` для локального тестирования.

Это **не** удалённое администрирование рабочего стола: экран, мышь, клавиатура и команды не передаются. MVP использует незашифрованный TCP без аутентификации; он предназначен только для изолированных тестов, не для реальных устройств или внешней сети. Подробности и ограничения — в [документации безопасности](security.md).

## Цели

1. Дать оператору интерфейс для безопасного подключения к разрешённой станции Windows.
2. Поддержать прямое сетевое соединение в локальной сети и через маршрутизируемый внешний адрес.
3. Предусмотреть проверку доступа учётной записью приложения или Windows и дополнительную двухфакторную проверку.
4. Не требовать центрального облака для установления канала управления.
5. Документировать настройки, риски и границы поддержки до предоставления доступа к устройству.

## Вне области первой версии

Следующие функции не считаются частью первой версии без отдельного решения:

- облачные учётные записи, обязательный relay-сервер или автоматическое пробрасывание NAT;
- скрытая установка, скрытое наблюдение или обход согласия пользователя;
- управление устройствами без разрешения владельца;
- удалённая установка обновлений, выполнение произвольных команд и передача файлов;
- мобильное приложение как операторский клиент;
- гарантированная работа за CGNAT или при запрете входящих соединений.

## Роли

| Роль | Ответственность |
|---|---|
| Оператор | Инициирует подключение, проходит проверку и выполняет разрешённые действия |
| Администратор станции | Устанавливает и настраивает компонент станции, определяет допустимый доступ |
| Пользователь станции | Может видеть активное подключение и завершить его согласно политике продукта |

В первой версии роли могут совмещаться одним человеком. Модель ролей и разрешений следует уточнить до разработки удалённых действий.

## Функциональные требования

### Подключение

- **FR-01.** [Реализовано для частных IPv4-адресов] Оператор указывает адрес и порт узла и инициирует прямое подключение.
- **FR-02.** [Реализовано] Локальный сценарий работает между устройствами, имеющими сетевой маршрут друг к другу.
- **FR-03.** [Не реализовано и запрещено в MVP] Внешний сценарий должен работать только при явной конфигурации владельца сети и после реализации безопасного протокола.
- **FR-04.** [Частично реализовано] Интерфейс показывает состояние соединения и ошибки подключения; расширенная диагностика и аудит ещё не реализованы.
- **FR-05.** [Частично реализовано] Пользователь видит входящий запрос, явно подтверждает его и может завершить сеанс; функций удалённого управления пока нет.

### Аутентификация и доступ

- **FR-06.** Спроектировать вход с учётной записью приложения.
- **FR-07.** Спроектировать проверку учётной записи Windows на самой управляемой станции.
- **FR-08.** Предусмотреть второй фактор с доставкой кода по SMS, электронной почте или через Telegram-бота.
- **FR-09.** Не считать успешную аутентификацию разрешением на все действия: права должны проверяться отдельно.
- **FR-10.** Ограничивать число попыток входа и защищать проверочные коды от повторного использования.

Для FR-08 требуется внешний канал доставки (оператор SMS, почтовый сервер либо Telegram Bot API). Это исключение из модели «без сторонних сервисов»: сетевой канал управления может быть прямым, но выбранный поставщик доставки фактора является внешней зависимостью. Каждый канал должен быть необязательным и явно настроенным владельцем.

### Сеансы

- **FR-11.** Сеанс начинается только после проверки подлинности и принятия политики доступа станции.
- **FR-12.** Завершённый или прерванный сеанс не должен оставлять активный доступ.
- **FR-13.** Система должна регистрировать события безопасности и административные действия без записи паролей, кодов и иных секретов.

## Нефункциональные требования

- **NFR-01.** Трафик аутентификации и управления защищён криптографически проверяемым каналом.
- **NFR-02.** Секреты хранятся и передаются с учётом рекомендаций для Windows; пароли не хранятся открытым текстом.
- **NFR-03.** При ошибке проверки сертификата или подлинности соединение отклоняется, а не продолжается в небезопасном режиме.
- **NFR-04.** Критичные операции доступны только после явной авторизации.
- **NFR-05.** Соединение устойчиво к потере сети: оно завершается безопасно, а не возобновляется с более слабыми настройками.
- **NFR-06.** Пользователь станции получает понятную индикацию текущего сеанса.
- **NFR-07.** Установка, запуск, обновление и удаление документируются для целевой версии Windows.
- **NFR-08.** Версия протокола и совместимость компонентов определяются до публикации стабильных сборок.

Численные цели производительности, перечень поддерживаемых выпусков Windows, локализация интерфейса и срок хранения журналов пока не определены.

## Критерии готовности первой версии

Первая версия не готова к внешнему использованию, пока не выполнены как минимум следующие проверки:

1. Установленный компонент Windows принимает соединение только по включённой администратором конфигурации.
2. Подключение работает в локальной сети и при явной конфигурации прямого внешнего доступа.
3. Нельзя обойти проверку идентичности стороны или продолжить соединение после ошибки проверки.
4. Подтверждены отдельные тесты для учётной записи приложения, Windows и каждого реализованного второго фактора.
5. Зафиксированы права каждой команды, журнал событий, блокировка перебора и процедура отзыва доступа.
6. Выполнены тесты установки, обновления, удаления, потери связи и восстановления.
